## The Problem

Peer-to-peer car rental sounds simple — list your car, someone rents it — but the trust and logistics problems are significant. The owner needs to know who's driving their car. The renter needs to know their payment is protected. And both sides need a booking system that won't double-book the same car on overlapping dates.

Existing solutions are either too simple (a Google Sheet and bank transfer) or too complex (enterprise fleet management software). There was no middle ground for a small marketplace that needed real payments, real authentication, and real availability management.

## The Approach

I built MoRent as a full-stack application: a Next.js 16 frontend over a FastAPI backend with SQLModel and Alembic migrations on Neon Postgres. It began as the CodeMigos cohort 6 build on Next.js 14, Prisma, and NextAuth; after the cohort I rebuilt the stack around FastAPI and self-hosted Better Auth while keeping the same core — a two-sided marketplace where owners list vehicles, renters browse and book, and a shared booking engine manages availability.

For payments, I used Stripe Checkout with the Payment Element. Fulfillment is driven by signature-verified webhooks with durable idempotency — a `webhook_events` table claims each event id before any business work, so Stripe's retries and duplicate deliveries can't double-confirm or drop a booking.

For authentication, I run Better Auth self-hosted in the frontend while FastAPI verifies JWTs via JWKS. The same account carries distinct customer and owner roles through the whole flow.

Availability checking is done at the database level with overlapping-date queries — the booking engine checks date conflicts atomically, and each listing carries a fleet quantity, so a multi-unit car only rejects bookings once every unit is held.

The project was built as part of CodeMigos cohort 6, deployed to Vercel with a live database.

## The Result

The app is deployed and functional: owners list vehicles, renters browse, book, and pay through Stripe Checkout, and bookings confirm through webhook fulfillment. The booking engine handles date-conflict prevention at the database level.

The full stack runs on Next.js 16, FastAPI, SQLModel with Alembic migrations, Neon Postgres, Better Auth, and Stripe — a production-grade stack for a marketplace where booking correctness under concurrency matters.

## Context

MoRent was built as part of CodeMigos cohort 6, a six-week intensive where the goal was a working, deployed product rather than a prototype. The brief was deliberately open: pick a domain with real transactional complexity and ship it end to end.

I chose a two-sided marketplace because it forces every hard backend problem into one project — authentication with multiple roles, payments with durable fulfillment, relational data with real constraints, and a booking engine where correctness matters. A CRUD app wouldn't have exercised those muscles.

The trust problem framed the whole design. In peer-to-peer rental, neither side knows the other. That means authentication has to carry roles end to end, payments can't be simple fire-and-forget charges, and availability has to be enforced at the database level rather than trusted to the client.

## Decisions & Trade-offs

**Stripe Checkout with durable webhook fulfillment over manual payouts.** I considered collecting payments and paying owners manually via bank transfer. Stripe Checkout keeps card data out of my infrastructure, and signature-verified webhooks with an idempotency claim on every event id make fulfillment safe to retry — duplicate deliveries are no-ops, and a crash mid-work lets Stripe's retry re-enter. Trade-off: webhook complexity and Stripe's fees, but the payment path is auditable end to end.

**Database-level overlap checking over application-level locking.** Checking for date conflicts in application code and then writing the booking leaves a race window between check and write. I used overlapping-date queries that run atomically in the database, so two concurrent bookings can't both succeed. Trade-off: a slightly more complex query, but correctness under concurrency.

**Server-side pricing over client-side quotes.** A quote assembled in the browser can drift from what the server charges. I price every booking server-side in integer cents — promo math included — and webhook fulfillment writes the stored totals. Trade-off: a round trip per quote, but the number the renter sees is the number they're charged.

## Reflection

The hardest part wasn't any single integration — it was making the booking engine correct. Double-booking is the failure mode that kills a rental marketplace, and the naive implementation (check, then insert) is subtly wrong under concurrency. Testing that path with simulated concurrent requests was the moment the project felt solid.

If I extended it, the next steps would be a review system after trips, inventory pricing rules (weekend vs weekday), and a refund path for contested bookings — payment is captured at checkout with idempotent webhook fulfillment, but a dispute flow would need its own handling.
