## The Problem

Learning physical AI and humanoid robotics means reading dense technical material — ROS 2 nodes, URDF models, Gazebo physics, Isaac Sim, Nav2 path planning. A static textbook can present the content, but it can't answer "what does this mean in context?" when a reader gets stuck on a specific passage.

Existing AI tutoring tools are generic — they answer from the LLM's general knowledge, not from the textbook's own content. The answers sound authoritative but aren't grounded in what the reader is actually studying. And they don't know which chapter you're reading, so they can't scope their retrieval to the relevant material.

## The Approach

I built an AI-native textbook: a Docusaurus site with 12 MDX chapters across 4 modules, and a FastAPI backend that powers a selection-aware RAG tutor.

**Selection-Aware RAG**: Highlight any passage in a chapter, click "Ask AI about this," and the chatbot answers using the retrieved chapter context plus your highlighted text. The retrieval is scoped to the chapter you're reading via a `chapter_id` filter — so answers come from the right material, not just any part of the book.

**Fully Local Retrieval**: Embeddings run in-process via ONNX Runtime (all-MiniLM-L6-v2, 384-dim) and vectors live in a local Qdrant instance. The only remote call in the answer path is the LLM through OpenRouter. No external vector DB, no embedding API.

**Streaming Answers**: `/api/chat` returns a `text/plain` stream that the chatbot appends token by token — you see the answer form in real time, not after a 5-second wait.

**Offline Incremental Ingestion**: Content hashes per MDX file mean unchanged chapters are skipped, edits are re-indexed, and deleted files are cleaned up. Re-ingesting a 12-chapter book takes seconds.

**Personalization & Translation**: A quiz builds a learner profile that drives chapter rewrites for your experience level. A translate action renders any chapter in Urdu (RTL) with fenced code blocks left untouched.

## Architecture

Two processes, one origin. The Docusaurus frontend proxies `/api` to the FastAPI backend in dev; in production, `vercel.json` routes `/api/*` to the Python backend and everything else to the static site.

The answer path is a single deep module (`chain.py`): lazy process-wide singletons for the Qdrant client, ONNX embedder, and vector store — built once on first use, not per request. The RAG chain factory accepts injected dependencies, so tests pass an in-memory retriever and a fake LLM with no monkeypatching.

## Testing

Backend: pytest suite (7 tests) covering chain wiring, chapter-filter structure, missing-key guard, and the `/api/chat` error path. Frontend: vitest + jsdom suites for Ask-AI state transitions, capture rules, and the chatbot consumer. Both suites run without real credentials or a live Qdrant.

## Decisions & Trade-offs

**Chapter-scoped retrieval over global search.** A global vector search would let a question about ROS 2 pull answers from the Gazebo chapter — technically relevant, pedagogically confusing. Filtering retrieval by `chapter_id` keeps answers grounded in what the reader is actually studying. Trade-off: cross-chapter questions ("how does this relate to Nav2?") get weaker answers since the relevant material may live elsewhere. The selection-aware path partially compensates — the highlighted passage anchors the query even within the chapter scope.

**Local ONNX embeddings over an embedding API.** Running MiniLM in-process means no per-embed API key, no rate limits, and offline ingestion. Trade-off: 384-dim local embeddings retrieve less precisely than larger hosted models on dense technical prose. For a 12-chapter book with clean MDX structure, chapter scoping does most of the heavy lifting, so the weaker embedder is acceptable.

**Docusaurus + separate FastAPI over a custom Next.js app.** Docusaurus gave me MDX chapters, sidebar navigation, search, and a static build for free — everything a textbook needs that I'd otherwise rebuild. The cost is a two-process architecture requiring proxy config in dev and `vercel.json` routing in production. Trade-off: more deploy complexity, but the writing experience and content structure are far better than a hand-rolled equivalent.

## Reflection

The design insight was that selection-aware retrieval solves a real problem generic chatbots don't: the reader's highlighted text is an unambiguous signal of intent that a typed question alone can't match. "What does this mean?" is useless without context; the same question plus a highlighted URDF snippet is precise.

If I extended it, I'd add cross-chapter retrieval as an explicit mode (ask "how does this relate to X?" beyond the current chapter), citation links that scroll to the retrieved source paragraph, and spaced-repetition flashcards generated from RAG retrievals of weak areas in the learner profile.
